## What actually happened

Phase 0 confirmed the exact pre-Block-4 baseline the run requires: root `aldc.yaml` present, no
`.github/aldc.yaml`, no `.external/`, extension `0.1.8-test.5` installed, `source.mode = localFork`
pointed at the correct fork, `bcquality.path`/`BCQUALITY_HOME` both absent, and the deliberately-wrong
`devRoot` left untouched. Exactly one BCQuality clone existed (489 files).

**Apply Toolkit** (Phase 1) ran in under a minute, produced two informational toasts (initialization
completed via local fork; a warning that the fork is on `feature/e006-bcquality` rather than `aproda`),
and performed the full migration cleanly: `.github/aldc.yaml`, `.external/README.md`, and a fresh
`.code-workspace.bak` all appeared exactly as expected, with no dialog blocking progress.

**Install/Update BCQuality** (Phase 2) took the update path with no confirmation prompt, left exactly
one clone in place, and the junction's actual `Target` (not just its existence) was verified to point
at the real clone — the precise check Run 2 lacked. Settings hygiene (Phase 3) was clean: both
`bcquality.path` and `BCQUALITY_HOME` agreed on the real clone, `linux`/`osx` carried no
`BCQUALITY_HOME`, and `Show BCQuality Status` gave a fully transparent, correct resolver-chain report —
notably it correctly flagged the deliberately-broken `devRoot` rung as "directory missing" instead of
silently resolving through it.

**Validate Installation** still fails to produce a verdict, now with `spawn EINVAL` instead of the
previously-reported `spawn npm ENOENT`. The symptom changed; the underlying defect (no verdict, ever)
did not.

The **negative test** (Phase 4) is where this run earns its keep. The maintainer set
`aprodaAldc.bcquality.path` to a non-existent path and confirmed it was saved, then ran
`Install / Update BCQuality`. No confirmation dialog appeared — the maintainer watched directly, so
this is not the "agent can't see modals" blind spot the briefing warned about. Instead, the command
silently rewrote the bogus setting back to the real clone path and reported success, with no
confirmation, warning, or log line about the correction. Investigation traced the mechanism: the
project's `.external/bcquality` junction (a lower-priority rung than the VS Code setting) already
resolves successfully from Phases 1–2, so the command never falls into the "nothing resolves, offer to
clone" branch the confirmation dialog is gated on — it just runs its normal update path and, as an
apparent side effect, re-syncs the setting to the value it actually used.

## Findings

- **[Major] C21 — "Validate Installation" still cannot produce a verdict.** Symptom changed from
  `spawn npm ENOENT` to `spawn EINVAL`; the command remains unusable either way. Not the same bug
  literally, but the same defect class (B-30 not actually fixed, just changed shape).
- **[Major] C15 — a Global setting is silently overwritten with no confirmation or log.** Setting
  `aprodaAldc.bcquality.path` to a non-existent path and running "Install / Update BCQuality" does not
  surface any warning about the misconfiguration; instead the command silently rewrites the Global
  setting back to whatever it resolved via another rung. Because this is a **Global**, not
  project-scoped, setting, a user could have deliberately pointed it elsewhere (e.g. testing a second
  clone, or intentionally overriding for another project) and have that choice silently discarded
  without any log line explaining why. This directly contradicts the intent of C15 ("the command must
  not have overwritten it").
- **[Minor / test-design gap, not a product defect] Phase 4 as written cannot be forced once Phase 1–2
  have already run against the same project in the same session.** The confirmation-dialog code path
  (C14/C16) is only reachable when *no* rung resolves — but after Apply Toolkit + Install/Update, the
  `.external/bcquality` junction rung always resolves successfully regardless of what garbage is put
  into `bcquality.path`. To genuinely exercise C14/C16, the junction itself would need to be removed
  first (sanctioned by briefing rule 5, `(Get-Item <path> -Force).Delete()`), which this run's
  instructions did not call for and the agent did not do unilaterally. Recommend either updating the
  Phase 4 instructions to explicitly break the junction first, or accepting that this negative path can
  only be tested on a project that has never had a working mount.
- **[Passed but worth flagging] The `$BCQUALITY_HOME` rung in "Show BCQuality Status" reported "not
  set"** even though `terminal.integrated.env.windows.BCQUALITY_HOME` was set. This is very likely
  correct — `terminal.integrated.env.*` only affects newly-spawned terminal shells, not the extension
  host process itself — but it's worth the maintainer confirming this is the intended read, since it
  could otherwise look like the setting isn't taking effect at all.
- **[Passed but worth flagging] File count 489→490 after Install/Update.** Traced to a freshly-written
  `.git/FETCH_HEAD` inside the real clone (a `git fetch` artifact), not a second clone. Not a defect,
  but the exact-match wording of C8 ("identical") is slightly too strict for a real `git`-backed clone
  that gets updated — recommend rephrasing the criterion to "same single clone path, delta explained by
  git-internal files" for future runs.

  command instead warn/log when overriding a user-configured `bcquality.path` that doesn't resolve?

- Should Phase 4 of this test file be revised to explicitly remove `.external/bcquality` before forcing

- Is `spawn EINVAL` on "Validate Installation" a regression from a different recent change, or was it
  never actually fixed by whatever addressed the original `spawn npm ENOENT` (B-30) — i.e., was B-30
