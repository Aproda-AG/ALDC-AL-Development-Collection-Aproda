## What actually happened

Phase 0 baseline matched the briefing closely, with one real surprise: a set of empty,
untracked `.github/*` scaffold directories already existed on disk before I started (git
doesn't track empty directories, so `git status` never surfaced them). The maintainer
identified these as stale from an earlier interrupted attempt and deleted them; the run then
proceeded from a genuinely clean slate.

Apply Toolkit ran cleanly and landed directly on the target T-33 shape: `.github/aldc.yaml`,
no root `aldc.yaml`, `.external/` with `README.md`, workspace file correctly updated
(folders, `.gitignore` block, backup byte-identical including the pre-existing trailing
comma). This is the first time this path has been exercised on a repo that never had ALDC
before, and it worked.

The BCQuality resolution chain, once actually invoked (manually), is solid: `Show BCQuality
Status` gave an honest, complete five-rung report; the wrong-`devRoot` trap surfaced exactly
as designed via a modal that named the bad path and was safely cancelled; pointing
`bcquality.path` at the real clone produced a silent, correct update with no duplicate clone,
a correctly-scoped `BCQUALITY_HOME` (Windows only), and a junction whose `Target` resolves to
the real clone. The knowledge layer worked end-to-end through the junction (`#bcquality`
read/list, `#aldcConfiguration`, and the search-exclusion holding).

Two things did not work: the **automatic** post-bootstrap BCQuality step during Apply Toolkit
logged nothing (not even "nothing to do") even though the underlying resolver logic is
demonstrably fine when invoked manually — and `Validate Installation` crashed with `spawn
EINVAL` instead of producing a verdict, on the very first real project this whole chain has
run against.

## Findings

- **Major — D30/D34, `Validate Installation` crashes (`spawn EINVAL`).** This is the one
  criterion the run explicitly flagged as historically broken (B-30, there as `spawn
  ENOENT`), and it is still broken, just with a different underlying spawn failure. No
  verdict was ever produced on this project. This should block release until fixed —
  "produces an actual verdict" was the bar, and it wasn't met.
- **Major — D18/D35, silent automatic BCQuality pass.** After Apply Toolkit, the output
  channel shows only `extension activated`, no line about the automatic BCQuality
  resolution attempt or its (legitimate) "nothing resolved" outcome. Verified not a
  log-level artifact (Trace tested explicitly, no change). Downgraded from "blocker" to
  "major" because the underlying decision itself is correct and fully inspectable via the
  manual `Show BCQuality Status` command, and manually-triggered actions (cancel, pull,
  link) *do* log — so the gap is narrowly "the automatic first-init pass doesn't announce
  itself," not a general logging defect. Still exactly the shape the briefing calls out as
  suspicious, and worth fixing so a user isn't left wondering if anything ran at all.
- **Minor — D15, split `search.exclude`.** The pre-existing workspace file had
  `files.exclude`/`search.exclude` as top-level keys (siblings of `settings`), which VS Code
  does not apply as workspace settings from that position — likely a pre-existing customer
  authoring defect, not something Apply Toolkit introduced. Apply Toolkit added its own
  `bcquality/**` exclusion in the *correct* location (nested under `settings`), but did not
  merge it into the old, differently-placed key. Net effect: the criterion's literal wording
  ("added to search.exclude") is satisfied by a new, correctly-scoped key existing
  side-by-side with an old, arguably-inert one — functionally fine, but worth a closer look
  by whoever owns the workspace-merge logic, since two keys with the same name at different
  nesting levels in one JSON file is an easy thing to misread later.
- **Nit — D1, stale empty scaffold directories on disk.** Not a defect in the run under test,
  but worth a note to whoever manages this test machine: leftover empty `.github/*`
  directories from an earlier session survived a git reset (git doesn't track empty dirs)
  and would have silently invalidated D1/D7 comparisons if not caught and removed manually
  before Phase 1.
- **Passed but worth flagging**: the two "local Aproda fork" warnings (feature branch,
  uncommitted changes) shown at Apply Toolkit time are correct and expected under
  `source.mode=localFork` for this test, but if this ever fires in a real customer session
  against an accidentally-misconfigured `forkPath`, the wording should make unambiguously
  clear that it is reading an uncommitted fork tree, not the released layer.
