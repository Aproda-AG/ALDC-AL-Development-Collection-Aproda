## What actually happened

Phase 0 found two real, unprompted deviations from the required baseline (a leftover `bcquality.path` / `BCQUALITY_HOME` from a previous run's reconcile, and the wrong extension build `.7` instead of `.8-test.8`). Both were corrected by the maintainer before proceeding, exactly as the briefing's C1 requires ("stop and report", not silently paper over).

Apply Toolkit ran once and, in this build, **already performed the BCQuality link as its last step** — the separate Phase 1 / Phase 2 split described in the run file has effectively collapsed into one operation for a first-time run. Migration (C6), the two long-missing files (C24), and the resolved-file count (C25 = 137) all came from this single execution. The explicit `Install / Update BCQuality` command was still exercised afterward and correctly took the no-op/update path (C7, C8).

The negative-test phase (Phase 4) worked as designed: a bogus `bcquality.path` did not get silently rewritten while the junction still resolved (Step A), and once the junction was deleted, the same bogus path produced a **named** confirmation modal that was safely cancelled with Esc, twice, without creating anything.

**One deviation from the run's own script surfaced during the restore step (Phase 4, Step B, item 4).** With the junction deleted and `bcquality.path` cleared (tested both as `""` and as a fully removed key — identical behavior), no rung could auto-recover the real clone, because `devRoot` is *deliberately* wrong for this run and `BCQUALITY_HOME` as a `terminal.integrated.env` setting does not populate the extension host's own process environment (confirmed via `Show BCQuality Status` showing `$BCQUALITY_HOME not set` even while the setting exists). The tool then proposed cloning to the devRoot-derived **wrong** path (`c:\_EphemeralWorkspace\BCQuality-Aproda`, missing the `Florian Köll` segment) — correctly *not* auto-cloning, just as B-23's fix intends, but this means "remove the setting to restore the junction" does not work unattended in this deliberately-misconfigured environment. Restoring required explicitly setting `bcquality.path` back to the real clone path. This is arguably the fix working as designed (it refuses to silently clone into a plausible-but-wrong location) rather than a defect — recorded as an open question below.

## Open questions

- Is the 489→490 file-count drift in the real clone (C30) benign (e.g., a git index/lock artifact) or worth investigating separately? Not one of B-23…B-37, flagging for the maintainer's judgment.
- Should the "uncommitted changes in the fork" notice (C3) be changed to non-blocking, matching the branch-mismatch notice's behavior, to fully satisfy C3 as written?
- Is the Phase 4 step-4 assumption ("remove the setting... to restore the junction") meant to work unattended, or was manual re-entry of the correct path always the intended recovery path when `devRoot` is wrong? The run file reads as if it should self-heal; it did not, for reasons described above.

## Maintainer assessment, 2026-09-28 — the result is better than the scorecard

*Added after the run, by re-measuring. **Nothing above is edited**: the verdicts stand as the runner
recorded them, and the reasoning that produced them was sound given the criteria it was handed. What
follows is the assessment of what those verdicts actually mean.*

**The two non-PASS verdicts are defects in my acceptance criteria, not in the product.** Both criteria
assert something other than what they were written to catch — the same "asserts existence, not
identity" failure class this epic keeps producing, this time in the test artifact rather than the code.

**C27 — re-measured, the criterion was wrong.** Independently re-run against the same project:

```
✓ AL naming: 503/507 files compliant
✅ ALDC Core v1.2 COMPLIANT (4 warning(s))
```

**Not one of the four is a fork-only warning.** All four are AL naming-convention misses in the
project's *own* source. `straub-medical-ag-base` has carried exactly these four since **2026-09-24**,
recorded under T-31 ("COMPLIANT, 4 warnings, 503/507 naming") — before any of this work started.
The six unresolvable fork-only warnings B-36/B-37 targeted are **gone**. I wrote "0 warnings" after

four since before the epic. I had that number in my own notes and wrote the criterion wrong anyway.
**C27 → PASS. B-36/B-37 confirmed in production.**

**C3 — the criterion conflates two different things.** The blocking dialog is `confirmGitHubChanges`
("Initialization can overwrite Aproda ALDC files. Continue / Cancel"). That is an **intentional
pre-flight gate**, and an earlier review named it explicitly as legitimately gating control flow, in
contrast to the advisory warnings B-24 removed. C3 was written to catch B-24's *advisory* notices and
phrased broadly enough to condemn the deliberate gate as well. **C3 → PASS.** The runner's own
observation — that the branch notice is non-blocking while this one is not — is exactly right, and that
asymmetry is the design, not a gap.

**Phase 4, step 4 — the runner's reading is correct.** "Remove the setting to restore the junction"
assumed a self-healing path that the B-23 fix deliberately removes: it refuses to clone into a
plausible-but-wrong `devRoot`-derived location. The instruction was wrong; the behaviour is the fix
working. **Observation, not a defect** — as recorded.

**C30 — 489 → 490 is `.git/FETCH_HEAD`.** Same drift, same cause, already traced in run 3.2. The
criterion's word "identical" is too strict for a git-backed clone that gets fetched.
