## 2. Asset update (X-02) — `tools/aproda-bc-data-access/Update-BcDataAccessAsset.ps1`

Maintainer script (fork-only). Input: path of a freshly built `.app`. Steps: read the manifest from the `.app` (name,
publisher, id, version — via the AL tool `altool GetPackageManifest <app>` as in the DRV engine, D-53 addendum);
verify name/publisher/id against `app/app.json`; refuse a version that is not higher than the current manifest;
remove the old asset; copy the new one to `skills/skill-aproda-bc-data-access/assets/`; write `app-manifest.json`:

```json
{ "appId": "<guid>", "name": "Aproda BC Data Access", "publisher": "Aproda AG", "version": "1.0.0.0",
  "minimumApplication": "25.4.0.0", "file": "Aproda AG_Aproda BC Data Access_1.0.0.0.app", "sha256": "<hex>" }
```

Build recipe (README): `al-mcp al_build projectPath=<fork>\tools\aproda-bc-data-access\app` with a package cache
copied from a project's `.alpackages` (Application, Base Application, Business Foundation, System Application,
System) — as in run 2 §3; then the script above.

## 3. Skill folder (X-03) — `skills/skill-aproda-bc-data-access/`

`SKILL.md` frontmatter:

```yaml
---
name: skill-aproda-bc-data-access
description: "Read live data of a customer's Business Central SaaS environment (sandbox or production, read-only) for support cases and root-cause analysis: setup tables, documents, ledger entries, PTE and table-extension fields, system tables such as installed apps or report selections. Signs in through the browser (Entra), installs a session-lived read-only helper app through the Automation API, runs table queries, and removes the app afterwards. Use when a diagnosis needs real customer data or setup instead of asking the user to look it up. Aproda custom skill (E-012, D-55)."
---
```

Sections (English, ALDC style, placeholders only — no tenant, account or customer value, F-2):

1. **Purpose and boundary** — SaaS only; read-only; not for OnPrem/Fkh (later); not for writes; the BC MCP Server
   note (BC 29, D-55 item 10).
2. **When to load** — support case / RCA needs live data; setup questions ("which report is configured…", "which apps
   are installed…", "which number series…"); verifying a hypothesis against real records.
3. **Prerequisites** — PowerShell 7; the account can manage extensions in the target environment (e.g. delegated
   *Dynamics 365 Business Central Administrator*, `D365 EXTENSION MGT` or SUPER); tenant id and environment name
   (from `launch.json` SaaS configurations, the BC URL, or the user).
4. **Session workflow** — the four commands of §0 with exact invocation (load content-based: `. ([ScriptBlock]::Create((Get-Content -LiteralPath <skill>\scripts\BcDataAccess.ps1 -Raw)))`,
   one command per terminal call; SRP: the module is loaded from the project folder, never copied to `$env:TEMP`).
5. **HITL acknowledgement** (D-55 item 7) — text template the agent shows before the install:
   *"Install the read-only helper app 'Aproda BC Data Access' into tenant `<tenant>` / environment `<env>` (`<type>`)
   for: `<purpose>`. It is removed with its data at the end of the session. Proceed?"* — production printed as
   **⚠️ PRODUCTION (read-only)**. The environment type is confirmed by the human (the Automation API does not report it).
6. **Query rules** — always one table set per request, only needed fields, small `top` for exploration; field names
   exact (lookup via the `Field` table, recipe in `rca-recipes.md`); filters in BC filter syntax; enum values by
   **name** (e.g. `S.Invoice`, not the caption); FlowFilters rejected; 1000-row cap, no paging/aggregation in v1.
7. **Data handling** (D-55 item 8) — results may appear in the chat; never write personal customer data into
   `plans/`, `documentation/` or any tracked file; diagnoses cite keys and setup values; large results with
   `-OutFile` go to the session folder only and are deleted by `Stop-…`.
8. **End of session** — always run `Stop-BcDataAccessSession` before closing the support case; if the user leaves
   earlier, tell them the app is still installed and how to remove it.
9. **Troubleshooting** → `references/troubleshooting.md`.

`AUTHORS.md`: original author Konstantin Prell (Relesta prototype: reader, API page, client), Aproda AG; adoption and
skill: Florian Köll. (Format as `skills/skill-aproda-ado/AUTHORS.md`.)

## 4. PowerShell library (X-04) — `scripts/BcDataAccess.ps1`

> **Implementation note (2026-11-13).** A `.ps1` library loaded content-based instead of a `.psm1`: SRP blocks path-based script/module loading on every Aproda workstation (site profile; same pattern as `skill-aproda-al-mcp`). HTTP, login, clock and delay sit behind small replaceable functions (`Invoke-BcdaHttp`, `Invoke-BcdaLoginPost`, `Receive-BcdaAuthCode`, `Get-BcdaNow`, `Wait-BcdaDelay`) so the tests run without network. Every call needs `-SkillRoot` only once (`Connect-…`); the session file remembers it.

Port of `bc-lib.ps1`, `Get-BcToken.ps1`, `bc-guard.ps1`, `bc-session.ps1`, `Install-DaApp.ps1`. PowerShell 7, no
external modules, strict mode, every public function returns objects (no `Write-Host` data). Output lines that the
agent parses start with a fixed prefix (`BCDA:`).

### 4.1 Session state

Folder `$env:TEMP\aproda-bcda\` (data only — SRP allows data files there; no script is ever written there):

| File | Content | Secret? |
|---|---|---|
| `token.txt` | access token only | **yes** — never printed, never copied |
| `session.json` | `tenantId`, `environment`, `environmentType` (as confirmed), `companyId`, `companyName`, `appId`, `packageId`, `installedAt`, `tokenExpiresAt` (display) + `tokenExpiresUnix` (logic — ISO strings are auto-converted by `ConvertFrom-Json`), `acknowledgedAt`, `purpose` | no |
| `out\*.json` | results written with `-OutFile` | personal data possible — deleted by `Stop-…` |

One session per workstation; a second `Connect-…` with another tenant/environment requires `Stop-…` first.

### 4.2 Public functions

| Function | Behaviour (from the measured prototype) |
|---|---|
| `Connect-BcDataAccess -SkillRoot <path> -TenantId <guid> -Environment <name> [-ClientId] [-DeviceCode]` | Auth code + PKCE (S256), free localhost port, `HttpListener`, `Start-Process` on the authorize URL (`prompt=select_account`, scope BC `.default offline_access`), state check, code redemption; writes `token.txt` and `tokenExpiresAt` from the token's `exp` claim; the refresh token is discarded. Listener timeout 5 min → `BCDA: LOGIN_TIMEOUT`. `-DeviceCode`: the colleague's flow as last fallback (prints the device message only). Prints only `BCDA: LOGIN_OK expires=<local time>`. |
| `Get-BcDataAccessCompany` | `GET <AutoApi>/companies` → `id`, `name`, `displayName`. |
| `Start-BcDataAccessSession -CompanyId <guid> -EnvironmentType Sandbox\|Production -Purpose <text> -Acknowledged` | Refuses without `-Acknowledged` (the agent passes it only after the human's yes). Reads the guarded state (4.3): **none** → install; **installed, version = manifest** → reuse (prints `BCDA: REUSE` — a previous session left it; the agent tells the human); **installed, other version** or **published-only packages** → guarded clean-up (4.4) then install; **guard failure** → stop. Install: SHA-256 of the asset = manifest, else `BCDA: ASSET_HASH_MISMATCH` and no upload; `extensionUpload` `{"schedule":"Current version","schemaSyncMode":"Add"}` → `PATCH …/extensionContent` (`application/octet-stream`, `If-Match: *`) → `POST …/Microsoft.NAV.upload`; poll `extensionDeploymentStatus` every 5 s, client-side filter by `name` and latest `startedOn` (the field is not filterable), timeout 10 min, `Failed` → status text verbatim; readiness: a trivial query (`Payment Terms`, field `Code`, `top` 1) every 5 s while HTTP 404 `BadRequest_NotFound`, max 3 min. Writes `session.json`. |
| `Invoke-BcDataQuery -Request <json> [-OutFile <name>]` | Validates the token (`exp` − 5 min) → else `BCDA: TOKEN_EXPIRED` (agent asks for `Connect-…` again; the session and the app stay). Body `{"id":"<new guid>","request":"<json string>"}` — **always** a new `id` (F-19). Returns the parsed `result` array; HTTP 400 → `BCDA: QUERY_ERROR <BC message verbatim>`; 404 → one readiness cycle, then `BCDA: API_NOT_FOUND`. With `-OutFile`: writes to `out\` and returns row counts only. |
| `Get-BcDataAccessState` | Guarded package list (version, `isInstalled`, `packageId`) + session file summary (no token). |
| `Stop-BcDataAccessSession [-KeepToken]` | Guarded clean-up (4.4), then deletes `out\`, `session.json` and — unless `-KeepToken` — `token.txt`. Prints the final state (`BCDA: CLEAN`). |

### 4.3 Identity guard (port of `bc-guard.ps1`, unchanged logic)

`Assert-BcDataAccessPackage <packageId>`: GUID format; `GET …/extensions(<packageId>)` = 200; `id` = manifest
`appId` **and** `displayName` = manifest `name` (case-sensitive) **and** `publisher` = manifest `publisher` **and**
`publishedAs.Trim()` = `PTE`; else throw `BCDA: GUARD <reason> - no call`. `Get-BcDataAccessPackages`: `GET
…/extensions?$filter=id eq <appId>` → every row through the guard. A `Dev`-published copy fails the guard
(troubleshooting: remove it in *Extension Management*).

### 4.4 Clean-up (port of `Invoke-EnsureClean -DeleteData`)

For each installed package: guard → `Microsoft.NAV.uninstallAndDeleteExtensionData` → wait until uninstalled
(2-s poll, 5 min). Then for every package of the app id: guard → `Microsoft.NAV.unpublish`. 404 tolerated
(`BadRequest_ResourceNotFound`). Ends with an empty guarded list or throws.

### 4.5 Secrets

The token is read only inside `Invoke-BcRequest` (private) from `token.txt` and passed as a header; no function
returns, prints or logs it; errors are rewritten so that no header appears. `Connect-…` never prints the auth code.
