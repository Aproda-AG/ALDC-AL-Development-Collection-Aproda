## 5. Breaking changes (to state in `CHANGELOG.aproda.md`)

| Change | Who notices | What to do |
|---|---|---|
| A `launch.json` configuration without `authentication` stops DRV (B-2) | Projects whose server configurations omit the field | Add `"authentication": "Windows"` or `"UserPassword"` |
| DRV config keys `launchConfig`, `server`, `serverInstance`, `tenant`, `scheme`, `authentication` → migration error (4a) | Every DRV project | Move the target into `aldc.local.json` (agent offers it), delete the keys, commit |
| `fkhSyncMode` now also applies to ASINST; the ASINST-only automatic `ForceSync` escalation is gone (D-39 unchanged otherwise) | ASINST redeploys with schema removals | The run stops with the schema message; the agent switches to `ForceSync` per D-39 and informs you |
| ASINST publishes through the Dev Endpoint; no uninstall/unpublish of older versions during deploy (4b) | ASINST projects | Leftover versions are listed by the one-time cleanup (§6 step 6) |
| Fkh deploy no longer uses `fkh publishapp` (Q-18) | Fkh projects | None — `fkh` still needed for target verification |

## 7. Rollback

| Situation | Action |
|---|---|
| Layer defect after release | Project: `aprodaAldc.channel = pinned`, `aprodaAldc.pinnedVersion = 1.2.0_aproda.17`, pull. The old engine needs its target back in the DRV config: re-add `launchConfig` locally (do not commit), keep `aldc.local.json` (ignored, harmless). |
| Extension defect | Install the `0.1.7` VSIX from the previous `vscode-ext/v0.1.7` release; or set `aprodaAldc.alMcp.start = manual` and do not start it — level 2 keeps working. |
| `altool` route defect only | `APRODA_DEPLOY_RUN_VERIFY_TEST_ROUTE=webClient` / `DEPLOY_ROUTE=devEndpoint` for the affected runs until a fix ships. |
