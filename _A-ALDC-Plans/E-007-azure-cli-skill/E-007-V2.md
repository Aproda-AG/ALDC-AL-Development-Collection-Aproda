# E-007-V2 — MCP-First Architecture for `skill-aproda-ado`

> **Status (2026-09-24):** **Implemented, reviewed, and fixed.** Supersedes **Phase 2** of
> [E-007-plan.md](E-007-plan.md) (the pure-`az`-CLI tier model); Phase 0 (org-URL fix) and the reasoning
> in [mcp-vs-cli.md](mcp-vs-cli.md) / [howto-setup-ado-mcp.md](howto-setup-ado-mcp.md) still apply. D-48
> recorded in `decisions.aproda.md` before implementation, per the D-16 process. An independent review
> (Claude Opus 5, read-only) found no blockers but 5 major issues — all fixed and empirically re-verified:
> an `--organization`/`-o` regex bug that re-opened F-1, two Tier-1 denylist bypasses (`--bypass-policy=true`,
> a concatenated `invoke` argument) in `Invoke-AdoAzCli.ps1`, and a documentation/config mismatch where
> setup instructions pointed into `_A-ALDC-Plans/` (a `neverTouch` path that never reaches a consumer
> project) with a stale `X-MCP-Toolsets`/`X-MCP-Readonly` example that would have blocked every MCP
> write — `readme.aproda.md` is now the canonical, shipping source for the MCP configuration. Several
> minor findings (BOM risk, a stray `$null` polluting `az` JSON output, an under-verified auth check, a
> missing PR-description-extraction step, wording inconsistencies) were fixed alongside.

## Relationship to V1

| V1 concept | What changes in V2 |
|---|---|
| 4 dedicated PS1 scripts, one per operation | Replaced by small composable **building blocks** (auth/preflight, parameter-safety, disclaimer, forbidden-check) + free az-CLI command composition guided by Agent Instructions |
| Tier model applies to `az` CLI only | Tier model now applies **uniformly to MCP and `az` CLI** — same policy, two backends |
| `az` CLI is the only backend | **MCP is primary** (when available), `az` CLI is the **fallback** |
| Phase 1 error-handling fixes (stale exit code, swallowed stderr, etc.) | Mostly moot for whatever routes through MCP (structured protocol, no shell-escaping); still relevant for the az-CLI fallback building blocks |
| Phase 3 (single auth-consolidation script) | Generalized into the az-CLI "building blocks" set below |

## Architecture

```
Agent Instructions (policy layer — identical for both backends)
├── Backend selection: MCP if the connection is configured and reachable, else az CLI
├── Tier policy: Read (4) / Trusted-on-request (2) / HITL-every-time (3) / Forbidden (1)
├── Recommended (not code-enforced) sequences: duplicate-PR check before create,
│   state preflight-read before a status change
├── az-CLI knowledge + snippet index (which building block for which intent)
└── Self-help sources (MCP + az CLI official docs)

Shared building block (backend-agnostic, always used before posting any comment)
└── Add-AdoAiDisclaimer — pure text transform, no API/CLI call itself, unconditional append

az-CLI building blocks (the fallback path)
├── Auth/preflight check (az present? azure-devops extension installed? login looks fresh?)
├── Parameter-safety helpers (fixed org URL default; @file trick for multiline/special-char content)
└── Invoke-AdoAzCli — the *only* sanctioned az-CLI entry point; checks the assembled argument
    list against the Tier-1 denylist (`devops invoke`, `--bypass-policy true`) before shelling out

MCP setup (the primary path, see howto-setup-ado-mcp.md)
└── Remote server, registered once at VS Code user level; X-MCP-Readonly / X-MCP-Toolsets
    scope the connection itself — the only technical (server-enforced) floor MCP offers
```

## Tier policy — unchanged intent, mapped to both backends

| Tier | az CLI | MCP tool | Enforcement |
|---|---|---|---|
| **1 — Forbidden** | `az devops invoke`; `az repos pr update --bypass-policy true`; `az repos policy *`; `az devops project *`; `az devops security permission *`; `az repos create/delete/update`; `az devops service-endpoint *`; `az pipelines create/delete`, `variable-group *`; `az boards work-item delete` | *(no generic `invoke`-equivalent tool exists in the ADO MCP catalog — structurally absent, not policy-blocked)*; the rest map to toolsets simply **not included** in `X-MCP-Toolsets` | az: code-enforced via `Invoke-AdoAzCli`'s denylist (only `invoke` + `--bypass-policy` — the rest have no code check, see note below). MCP: connection-level toolset scoping, server-enforced |
| **2 — Trusted (on-request only, not automatic)** | `az repos pr create`; `az boards work-item update --discussion @file` (comment); `--state ...`; `az repos pr reviewer add`; `az repos pr set-vote`; `az repos pr update --description/--title` (non-merge fields) | `repo_pull_request_write create`; `wit_work_item_comment_write add`; `wit_work_item_write update` (state field); `repo_pull_request_write update_reviewers`; `repo_pull_request_write vote`; `repo_pull_request_write update` (non-merge fields) | Standard preview-and-approve gate (Agent Instructions), disclaimer building block always runs first for comments |
| **3 — HITL every time** | `az pipelines run`; `az repos pr update --status completed`/`--auto-complete true`; `az boards work-item create`; field updates; `relation add` | `repo_pull_request_write update` (incl. auto-complete — same bundling problem as `az`); `wit_work_item_write create`; `wit_work_item_link_write *` | Explicit confirmation per call, self-verified per D-35 |
| **4 — Read** | any `show`/`list`/`query` | any read-only tool (`repo_pull_request`, `wit_work_item`, `wit_query`, …) | Always allowed, no gate |

> **Note on the az-CLI Tier-1 list:** per the "az CLI bissl strikter" trade-off accepted in this
> conversation, only `az devops invoke` and `--bypass-policy true` are **code-checked** by
> `Invoke-AdoAzCli`. The rest of the Tier-1 list (policy/security/repo-lifecycle/pipeline-definition
> commands) has **no code check** on the az-CLI path — it relies entirely on Agent Instructions plus
> ADO's own server-side permission model as the backstop, same reasoning already accepted for
> PR-completion in the original tier design. This is a conscious, accepted gap, not an oversight.

## The two-layer enforcement model (stated explicitly, not implied)

1. **Soft (instructional):** "Writes always go through `Invoke-AdoAzCli` / the disclaimer building
   block / the MCP connection as configured — never a raw, unwrapped call." This layer can in principle
   be bypassed by an agent that ignores its own instructions (same limitation the 4 V1 scripts already
   had — nothing stopped a raw terminal `az` call bypassing them either).
2. **Hard (code, only once Layer 1 is followed):** the denylist check inside `Invoke-AdoAzCli` and the
   unconditional append inside `Add-AdoAiDisclaimer` cannot be parameterized away — no flag suppresses
   them once the sanctioned path is actually used.

MCP has no equivalent to Layer 2 at the per-call level — its only genuinely server-enforced floor is the
connection-level `X-MCP-Readonly`/`X-MCP-Toolsets` configuration (set once at setup, not per call).

## What is deliberately no longer code-enforced (accepted trade-off)

- **Duplicate-PR check** before `pr create` (today hardcoded in `Create-AdoPullRequest.ps1`) → becomes a
  documented recommended step in Agent Instructions.
- **State preflight-read** before a work-item status change (today hardcoded in
  `Update-AdoWorkItem.ps1`) → same, becomes instructed rather than enforced.

These are safety/UX features, not security blockers — acceptable to soften given the overall shift away
from long dedicated scripts, as long as it's a conscious choice (this note is that record).

## Open questions — resolved (2026-09-24)

1. `az repos pr set-vote` / MCP `repo_pull_request_write vote` → **Tier 2** (trusted, on-request only — same rule as State/Reviewer: the agent calls this only when the user explicitly asks for a vote, never automatically). Reflected in the tier table above.
2. `az repos pr update --description/--title` / MCP `repo_pull_request_write update` (non-merge fields) → **Tier 2** (same on-request-only rule). Reflected in the tier table above.
3. `Title` sanitization fallback — **verified empirically 2026-09-24**, not just asserted from the
   generic-convention docs. MS Learn confirms `@<file>` is a **generic Azure CLI argument-loading
   convention**, not a per-command opt-in: *"the best practice is to use Azure CLI's `@<file>` convention
   to load from a file to bypass the shell's interpretation"*
   ([Considerations for running the Azure CLI in a PowerShell scripting language](https://learn.microsoft.com/cli/azure/use-azure-cli-successfully-powershell)).
   Confirmed with a real throwaway PR (Gustav Gerig AG / Gustav Gerig AG Base, PR #21693, created via
   `ConvertTo-AdoFileArgument.ps1` + `Invoke-AdoAzCli.ps1`, then deleted): title
   `E-007 test: & < > "quotes" and a colon: verify @file survives (DELETE ME)` round-tripped exactly
   intact through `--title @<file>`, working the same way it already does for `--description`.

## Governance

Same as V1: `skill-aproda-ado/` matches `skill-aproda-*/**`, so this is a D-16 layer edit. Given the scope
of this redesign (new backend, new building-block shape, policy now spans two systems), this needs its
own decision entry (proposed **D-48**, superseding the narrower one drafted for V1's Phase 2) and explicit
maintainer confirmation before any implementation starts.

### D-48 text (added to `decisions.aproda.md`; kept here for the design trail)

> ### D-48 — Hybrid MCP/az-CLI architecture with a tiered write policy replaces the narrow 2-command allowlist
>
> **Context.** `skill-aproda-ado` (D-4) originally exposed exactly 2 write operations through 4 fixed
> PS1 scripts, with a blanket "Forbidden: everything else" clause. E-007 found the fixed scripts carried
> a parameter-format bug (bare org name vs. the fully qualified URL `az --organization` requires) that
> looked like a permissions problem, and that the design structurally cannot reach PR-thread comments —
> no such `az` command exists at all. The official Azure DevOps MCP Server covers that gap and offers
> broader read/write tool coverage via a Microsoft-hosted, Microsoft-maintained endpoint requiring no
> local install.
>
> **Decision.** Adopt a hybrid backend: MCP preferred when its connection is reachable, `az` CLI as
> fallback. Both are governed by one shared tier policy — Read (4, always allowed) / Trusted-on-request
> (2: PR create, comment, state change, reviewer-add, vote, non-merge PR-field edits — never automatic)
> / HITL-every-time (3: PR merge/auto-complete, work-item creation, field updates, relations) / Forbidden
> (1: policy, permissions, repo-lifecycle, pipeline-definition, and service-connection commands, plus
> `az devops invoke` as a standalone hard carve-out since it is a raw REST passthrough with no MCP
> equivalent to reason about). Enforcement is two-layered: an instructional layer (route writes only
> through the sanctioned building blocks) plus a code layer that is unconditional once that path is used
> (the AI disclaimer append; the `invoke`/`--bypass-policy true` denylist inside the az-CLI wrapper). The
> 4 original operation-specific scripts are replaced by small composable building blocks (auth/preflight,
> parameter-safety, disclaimer, forbidden-check).
>
> **Rejected alternative.** Keep `az` CLI as the only backend and simply widen its allowlist — rejected
> because it can never reach PR-thread comments/votes (structurally absent from the CLI, not a policy
> choice), and because MCP's connection-level `X-MCP-Readonly`/`X-MCP-Toolsets` scoping is a genuine,
> Microsoft-enforced technical floor that a pure-CLI design cannot obtain for free.

## Rollout / Onboarding

Where the MCP setup gets surfaced to a human, and how the agent behaves at runtime when it isn't set up
yet. Three surfaces, with different governance:

| Surface | Change | D-16-gated? |
|---|---|---|
| `tools/aproda-vscode-extension/package.json` — Get Started walkthrough | New step **"Set up recommended MCP servers (one-time setup)"**, placed **before** the existing `azureCliSetup` step — MCP is now the primary path, CLI the fallback, so the walkthrough order should reflect that instead of the historical order (CLI existed first, MCP is the later addition). Covers all three worthwhile MCP servers together, not just `ado`: `microsoft-learn` + `context7` (zero-config, no auth) and `ado` (org-specific URL + one-time interactive Entra sign-in). One copy-to-clipboard command (`copyRecommendedMcpServers`, mirroring the existing `copyAdoCliSetupCommand` pattern) copies all three as a **JSON fragment** (just the inner `"microsoft-learn": {...}, "context7": {...}, "ado": {...}` entries, not a wrapping `{ "servers": {...} } }` document) so it merges safely into whatever a dev already has in their user `mcp.json` instead of risking an overwrite. Reference [howto-setup-ado-mcp.md](howto-setup-ado-mcp.md) for the exact content. No linked command otherwise — mark done manually. |
| `tools/aproda-vscode-extension/package.json` — `azureCliSetup` step (existing) | Re-worded from "Required only for …" to **"Recommended as a fallback"**: `skill-aproda-ado` prefers MCP when reachable; az CLI keeps ADO access working when MCP isn't (network/proxy blocking `mcp.dev.azure.com`, server outage, or before MCP is configured on a given workstation) — not something to skip once MCP is set up. Already has its own copy-to-clipboard command (`copyAdoCliSetupCommand`) fixing the "can't select text out of a walkthrough code block" issue found separately. | ❌ No — matches neither `.aproda.*` nor `skill-aproda-*/**`; the extension has its own release process |
| `onboarding.aproda.md` | New parallel section "1c — Recommended MCP servers" (placed **before** "1b — Azure CLI einrichten", matching the new walkthrough order and the "MCP primary, CLI fallback" framing — re-word 1b the same way as the walkthrough step above) | ✅ Yes (`.aproda.` in filename) |
| `skill-aproda-ado/SKILL.md` | Prerequisites section gets an MCP path alongside the az-CLI path; **agent runtime behavior**, confirmed: check once per session whether the `ado` MCP connection is reachable — if yes, prefer it per the Tier-to-tool mapping above; if no, offer the setup **once** (not repeated nagging) with a pointer to the walkthrough step / `howto-setup-ado-mcp.md`, then continue that session via the az-CLI fallback regardless of the answer | ✅ Yes (`skill-aproda-*/**`) |

Nothing above is implemented yet — this section only records the agreed shape so the three surfaces move
together instead of drifting (e.g. the walkthrough mentioning MCP before the skill knows how to detect it,
or vice versa).
